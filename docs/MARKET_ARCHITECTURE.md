# معمارية البيع أونلاين — سيلا ماركت (Sela Market)
## وثيقة التصميم والتحليل — الإصدار 1.0 (الجولة 56)

> هذه الوثيقة تشرح آلية العمل الكاملة لربط تطبيق نقطة البيع «سيلا» بمتجر
> المستخدمين (تطبيق المتجر القادم): كيف يُنشأ حساب التاجر ويربط بالمتجر،
> كيف تتزامن المنتجات، كيف تُدار الطلبات والدورة المحاسبية الكاملة، وكيف
> تُحمى المنصة عند انتهاء الاشتراك — دون أي تداخل بين حسابات نقاط البيع
> أو المستخدمين.

---

## 1) المكونات الثلاثة

| المكوّن | الجهة | الوصف |
|---|---|---|
| **تطبيق نقطة البيع سيلا** | التاجر | تطبيق Android الحالي (com.sela.pal) + وحدة «البيع أونلاين» الجديدة |
| **خادم سيلا** (sela-license-server) | الإدارة | خادم واحد على Coolify: تراخيص + اشتراكات + **منصة المتجر** (هذا التطوير) |
| **تطبيق المتجر** (سيلا ماركت) | المستخدم العادي | تطبيق Android منفصل — **المرحلة القادمة** — يبنى فوق واجهات API الجاهزة هنا |

**القرار المعماري:** منصة المتجر تقيم داخل نفس خادم التراخيص لثلاثة أسباب:
1. **هوية التاجر = مفتاح اشتراكه** — الخادم يعرف المفتاح والجهاز وحالة
   الاشتراك أصلاً، فلا حاجة لنظام حسابات ثانٍ للتاجر (فكرة التاجر نفسه:
   «من خلال مفتاح الاشتراك ومعرف الجهاز»).
2. **حماية النشر بالاشتراك:** إلغاء/انتهاء الاشتراك يجب أن يوقف نشر
   المنتجات فوراً — الحالة تعيش في نفس قاعدة البيانات (جدول keys).
3. **تشغيل واحد:** نشر Coolify واحد، مجلد بيانات واحد (/data)، نطاق واحد،
   نسخ احتياطي واحد — لا تعقيد إضافي على الإدارة.

## 2) ربط التاجر بالمتجر (إنشاء حساب المتجر)

```
تطبيق POS (الإعدادات → البيع أونلاين → تفعيل)
   │  POST /api/v1/store/register
   │  { license, signature, deviceId,
   │    store: {name, description, category, region, phone, whatsapp},
   │    deliveryRegions: [{name, fee}, …] }
   ▼
الخادم يتحقق: التوقيع صحيح + الربط (key+device) نشط + المفتاح غير موقوف
   ▼
ينشئ/يحدّث صف stores (مرتبط بـ key_id — متجر واحد لكل مفتاح)
   ▼
يرجع storeId + storeNumber (مثال: ST-000123)
```

- **التحقق الصامت:** كل نداء تجاري يمر عبر نفس زوج (license, signature,
  deviceId) المستخدم في نبضة الترخيص — التاجر لا يدخل أي بيانات دخول.
- المتجر يحمل عنوان صفحة خاصة به `storeNumber` تعرضها POS للتاجر
  (تُستخدم لاحقاً كرابط/QR في تطبيق المتجر).
- **تعطيل البيع أونلاين** من POS يرسل `published: false` فتُخفى منتجات
  المتجر من المتجر فوراً دون حذف شيء.

## 3) مزامنة المنتجات (دورية + عند الطلب)

- كل **15 دقيقة** أثناء عمل التطبيق + عند كل تعديل كتالوج + يدوياً بزر
  «مزامنة الآن».
- `POST /api/v1/store/products/sync` — إرسال الكتالوج الكامل (غير المؤرشف):
  الاسم، التصنيف، سعر المفرق، المخزون، الباركود، وحدة البيع، وزن/قطعة،
  وصف اختياري. **idempotent** بمفتاح `product_ref` (معرّف المنتج المحلي).
- المنتجات الغائبة عن المزامنة تُعلَّم «غير متاحة» ولا تُحذف — تعود
  متاحة عند ظهورها مجدداً (لا فقدان تقييمات/طلبات تاريخية).
- المخزون على الخادم **لقطة آخر مزامنة** (للعرض)، والمصدر الحقيقي هو
  POS: عند «إرسال» الطلب تتحقق POS من المخزون داخل معاملة البيع نفسها،
  وإن لم تكفِ يُرفض الإرسال بسبب واضح يراه المستخدم.
- الصور: منتجات POS قد تحمل صوراً محلية؛ ترفع مصغرة مضغوطة ضمن المزامنة
  (اختياري لاحقاً) — النص والسعر والمخزون أولوية المرحلة الأولى.

## 4) المستخدم العادي وتطبيق المتجر (المرحلة القادمة)

- التسجيل: **رقم هوية فريد + الاسم + رقم الجوال** (`market_users`، رقم
  الهوية UNIQUE عالمياً — مستخدم واحد لكل هوية عبر كل المتاجر).
- التصفح: واجهات عامة جاهزة الآن:
  - `GET /api/market/stores` — المتاجر المنشورة (اشتراك فعّال فقط)
  - `GET /api/market/stores/:id/products?category=&q=&page=`
  - `GET /api/market/products?q=&category=&page=` — بحث عابر للمتاجر
    («يصفح بين الآف المنتجات من مئات نقاط البيع»)
  - `GET /api/market/categories` — التصنيفات المجمعة
  - `GET /api/market/stores/:id` — صفحة المتجر الخاصة + مناطق التوصيل
- الطلب: سلة لكل متجر (طلب منفصل لكل متجر حتى لا تتداخل الطلبات بين
  التجار — «التمييز بين المنتجات والتجار») مع منطقة التوصيل التي يختارها
  فيُضاف سعر التوصيل الذي ضبطه التاجر لتلك المنطقة إلى فاتورته.

## 5) دورة حياة الطلب والحركة المحاسبية

الحالات: `new → accepted → sent → delivered` أو `rejected / cancelled /
returned (كلي/جزئي)`.

| الخطوة | من يفعلها | أثرها على POS (سيلا) | أثرها على الخادم |
|---|---|---|---|
| طلب جديد | المستخدم | إشعار نظام + شارة على زر الطلبات | status=new |
| **قبول** | التاجر | لا كتابة محلية بعد | accepted (+وقت) |
| **رفض** (بسبب) | التاجر | لا شيء | rejected + reason |
| **إرسال/تجهيز** | التاجر | **فاتورة INV-O** (سلسلة أونلاين) + خصم المخزون + تسجيل في مبيعات اليوم + **دين أونلاين مؤقت** — كلها في معاملة واحدة | sent + invoice_ref |
| **تأكيد التسليم** | التاجر | **ترحيل المبلغ من الدين إلى الخزينة**: سند تحصيل أونلاين (COLL) نقد داخل + تصفير دين الطلب | delivered |
| **إلغاء قبل الإرسال** | المستخدم/التاجر | لا شيء محلياً (لا فاتورة بعد) | cancelled |
| **إرجاع كلي/جزئي بعد الإرسال** | التاجر | مسار الإرجاع القياسي (RET-) على فاتورة INV-O بضابط `online`: إعادة للمخزون + تنقيص الدين (قبل التسليم) أو استرداد نقدي من الخزينة (بعد التسليم) | returned + المبالغ |
| **استبدال** | التاجر | مسار الاستبدال القياسي بضابط online — البضاعة تخرج ويُسوّى الفرق مالياً | يبقى delivered مع مرتجع |

**المبادئ المحاسبية (مطابقة لقواعد سيلا الحالية):**
- البيع أونلاين **بيع عادي بكل المميزات**: ربح اليوم، أفضل المنتجات،
  التقارير اليومية/الساعية — كلها تحسب INV-O مثلها مثل INV.
- الدين الأونلاين **مؤقت بالتعريف**: قائم فقط بين «إرسال» و«تأكيد
  التسليم»؛ يظهر كسطره الخاص في بطاقة الديون بالرئيسية والتقارير.
- تحصيل الطلب **ليس إيراداً** بل مقبوضات (قاعدة Square/Loyverse المتبعة
  في التطبيق): يدخل النقد بالخزينة عبر سند COLL ويُستبعد من مبيعات
  الفترة لأن الفاتورة حُسبت يوم الإرسال.
- الإرجاع يُسند لفترة فاتورة INV-O الأصلية (نفس قاعدة v30) فلا تفسد
  مبيعات اليوم عند إرجاع طلب قديم.

## 6) حماية المنصة وعزل الحسابات

1. **عزل المتاجر:** كل طلب مقيّد بـ store_id، وكل نداء تجاري يعيد فقط
   بيانات متجر المفتاح نفسه — لا يمكن لنقطة بيع رؤية طلبات أو منتجات
   أو مستخدمي نقطة أخرى.
2. **عزل المستخدمين:** المستخدم يرى طلباته فقط (برمز جلسة شخصي).
3. **النشر مربوط بالاشتراك:** مهمة دورية (كل 10 دقائق) + فحص لحظي عند كل
   مزامنة/استطلاع: مفتاح منتهٍ/موقوف → `published=0` فتختفي المنتجات من
   المتجر. العودة تتطلب اشتراكاً فعّالاً (إعادة تفعيل من POS).
4. **الطلبات مرقمة فريدة** عالمياً `ORD-YYYYMMDD-XXXXXX` وكل تغيير حالة
   يرفع `revision` — نداءات POS idempotent (إعادة الإرسال آمنة شبكياً).
5. **لا تداخل مع دفاتر صلة/المتجر:** الديون الأونلاين دفتر مستقل ثالث
   (INV-O) — دفتر صلة (INV-D) ودفتر المتجر (INV-L) لا يمسهما شيء.

## 7) واجهات API — الخلاصة التنفيذية

**تجارية (POS — مصادقة license+signature+deviceId):**
```
POST /api/v1/store/register        إنشاء/تحديث ملف المتجر + مناطق التوصيل
POST /api/v1/store/products/sync   مزامنة الكتالوج (idempotent)
POST /api/v1/store/orders/poll     طلبات جديدة/محدثة منذ مؤشر
POST /api/v1/store/orders/action   قبول/رفض/إرسال/تسليم/إلغاء (+invoice_ref)
```

**عامة (تطبيق المتجر):**
```
GET  /api/market/stores · stores/:id · stores/:id/products
GET  /api/market/products · categories
POST /api/market/auth/register {idNumber, name, phone} → token
POST /api/market/auth/login    {idNumber, phone}        → token
POST /api/market/orders        {storeId, items[], regionName, address, note}
GET  /api/market/orders        (token) طلباتي
POST /api/market/orders/:id/cancel  (token، قبل الإرسال فقط)
```

**إدارية (لوحة التحكم):** قسم «المتاجر» — قائمة المتاجر وحالة اشتراكها،
عرض الطلبات، نشر/إخفاء يدوي، وإحصاءات المنصة.

## 8) ما نُفِّذ في هذه الجولة (56)

- **الخادم (v4.0):** جداول المنصة السبعة + الواجهات التجارية والعامة
  كاملة + الحارس الدوري للنشر + قسم المتاجر باللوحة + اختبار تكاملي
  end-to-end (تسجيل تاجر → مزامنة → تصفح → طلب → قبول → إرسال → تسليم →
  انتهاء اشتراك → إخفاء المنتجات).
- **نقطة البيع (v48):** إعدادات البيع أونلاين (تفعيل، ملف المتجر، مناطق
  التوصيل بأسعارها)، محرك المزامنة والاستطلاع مع إشعارات الطلبات، صفحة
  الطلبات بفلاترها وتفاصيلها وأزرار قبول/رفض/إرسال/تسليم/إلغاء مع الاتصال
  بالزبون بلمسة، الفاتورة INV-O والدين المؤقت وسند COLL، زر وصول سريع
  في الرئيسية مع شارة الطلبات الجديدة، ودمج كامل في التقارير والخزينة.
- **البنية جاهزة الآن للتسليم** لتطبيق المتجر (المرحلة التالية) فوق نفس
  النشر على Coolify دون أي تغيير خادمي إضافي.
